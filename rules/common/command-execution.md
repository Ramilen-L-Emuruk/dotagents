# コマンドの実行と結果の読み方

コマンドやツールを走らせるときの落とし穴。中心は**成功したかどうかを何で判断するか**で、
「エラーが出なかったから通った」で進めると、通っていない結果を材料にして先へ進むことになる。
あわせて、Windows と Excel で**成否が見た目から分からない**ケースを扱う。

> 「日本語を含むパスが渡らないことがある」は Windows 固有、「既存の Excel ブックを書き換えるとき」は
> Excel を扱う場合の話。当てはまらない環境では読み飛ばしてよい。

## 終了コード 0 を成功と決めつけない

**終了コードは、コマンドが「自分の仕事を終えた」ことしか表さない。** 目的を果たしたかは別。

実例（Subversion 1.14.5 で実測）: **作業コピーの中の存在しないパス**を `svn status` に渡すと、
**出力は空、終了コードは 0、警告も出ない**。「対象が無い」と「対象を見に行けていない」が同じ見た目になる。

**成功とみなす条件を、コマンドごとに 3 つ揃えてから使う。**

1. **終了コードが 0**
2. **出力にエラーの印が無い** —— そのコマンドがエラー・警告を出すときの形（`svn:` や `svn: warning:` で始まる行、
   `error:` など）が 1 行も無い。PowerShell から外部コマンドを呼ぶ場合は `NativeCommandError`
   （外部コマンドが標準エラーへ出した内容を PowerShell がエラーとして包んだときの型名）も印になる
3. **目的を果たしたときにだけ出る印がある** —— 処理した件数、作成・更新されたパスの表示、取得した値そのもの

**3 に使えるのは「対象が実在したこと」を示す出力だけ。** 対象の有無にかかわらず必ず出る見出しや
決まり文句は印にならない（上の `svn status -u` は、存在しないパスでも「何リビジョンに対しての状態か」を
示す行を出し、終了コードも 0 になる。実測で確認した）。

**3 が無いコマンドは、3 で判定できない。** その場合は、結果を別のコマンドで確かめる。
同じ対象に対して**失敗を終了コードで返すコマンド**があれば、それを使う
（`svn` なら `status` ではなく `info` が、存在しないパスに対して終了コード 1 を返す）。

**1 つでも欠けたら失敗として扱い、その結果を後続の材料にしない**（3 が無いコマンドは、上記のとおり
別の確認で代える）。

## 日本語を含むパスが渡らないことがある（Windows）

非 ASCII を含むパスを外部コマンドへ渡すと、「ファイルが見つからない」という形で失敗したり、
返ってくる出力が化けたりすることがある。**コマンドの書き方ではなく、文字コードの食い違いが原因**なので、
引数の書き方を変えても直らない。

**まず、入力側（引数が渡っていない）か出力側（返りが読めない）かを切り分ける。** 対処が違う。

| 症状 | どちら | 見分け方 |
|---|---|---|
| 「見つからない」と言われるが、そのパスは確かに存在する | 入力側 | ASCII だけのパスに置いて同じコマンドを試す。通れば入力側 |
| 処理は動いたが、返ってきた文字が化けている | 出力側 | 出力をファイルへ書いて、そのファイルを読む。正しく読めれば出力側 |

**出力側なら、結果をファイルへ書いて読む。** エラー出力も含めて UTF-8 で書き、そのファイルを読む。
置き場所は**作業対象の外**（一時作業用のディレクトリ）——作業対象の中に置くと、バージョン管理の差分や
成果物に混ざる。

**入力側なら、コンソールの文字コードを切り替える手がある。** ただし**切り替え先の値も、何を切り替えれば
効くかも環境による。** 自分の環境で 1 度試して効くことを確かめてから使うこと。

**切り替える前に、いまの値を控える。** 切り替えたら**必ず元へ戻す**——設定はコンソールに残り、
後続の呼び出しへ影響する。**次の呼び出しの最初に、戻っているかを確かめる**（途中で止まると戻らないため）。

> **引数の `$` が消えるのは、文字コードとは別の原因。** パスを `"` で囲むと `$` から始まる部分が
> 変数として解釈されて消えるので、`'` で囲む（Excel が開いている間に作られる `~$<ブック名>` のような
> ファイル名で実害が出る）。

## 応答が返らないコマンドは、呼ぶ前に打ち切り方を決める

ネットワーク越しのコマンド（リモートのバージョン管理・外部サービスの取得）は、**相手へ届かないと
エラーも返さずに止まる**ことがある。

**止まってから手は打てない。** 同期実行中のコマンドは途中で止められないので、**呼ぶ前に決めておく**。

- **短いタイムアウトを付けて呼ぶ**（応答が無いことを、待ち続けずに失敗として受け取れる）
- または**バックグラウンドで起動して、後から結果を見に行く**

打ち切られたら、何を実行して止まったかをユーザーへ伝える。**黙ってもう一度叩かない**
——届かない原因（接続・資格情報）はたいてい再実行では変わらない。

## 既存の Excel ブックを書き換えるとき

**ライブラリで保存すると、ライブラリが解釈できない要素が落ちる。** Python の `openpyxl` で開いて
保存し直すと、**条件付き書式の一部が消える**ことがある（ブックによる）。**崩れは保存した時点では
分からず、後で人が開いたときに気づく。**

- **書き込みは Excel 本体を操作して行う**（Windows なら COM 経由。Excel が入っていない環境では
  この方針が取れないので、壊れる可能性を承知で進めるかをユーザーに確認する）
- **`openpyxl` は読み取りだけに使う。** 読み取りでも、開いて保存し直さないこと
- 書き込む前に、**元のブックの写しを取る**。置き場所は作業対象の外
- **合計を計算するセルは、見た目が入力欄と同じことがある。** 色や枠では見分けられないので、
  どのセルが数式かを確かめてから書く
- **数式を別の行へ写すときは、相対参照が行に合わせてずれる方法を使う**（コピー貼り付け、オートフィル、
  範囲への一括代入など）。**セルごとに元の行の数式文字列（`=B5*C5`）をそのまま代入すると、
  参照は元の行を指したまま**になり、値は入っているように見える。
  **1 行試して、写した行が自分の行を参照しているかを確かめてから**本番に掛ける
- **保存したら開き直して確かめる。** 書き込みの成否は、書いた直後の戻り値では分からない
